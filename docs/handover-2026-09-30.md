## Facts established by probing

### Per-device data

| device type | what it actually reports |
|---|---|
| `ENERGY_STORAGE_INTEGRATED_CABINET` | full inverter telemetry (`pac`, `ppv1-4`, `vpv1-4`, `ipv1-4`, `vac1`, `iac1`, `fac1`, `tempperature`, `hour_total`) |
| `BATTERY_RACK` | telemetry only while online: `pbattery`, `vbattery`, `soc`, `soh`, `bms_temperature`. Counters: `eChargeDay`, `eDischargeDay`, `echarge_total`, `edischarge_total`. An **offline** rack returns only its serial |
| `DONGLE` | nothing. Both telemetry and telecounting return `{}`. Only `status` from the device list |
| `SMART_METER` | `meter_power`, `meter_phase_{a,b,c}_{power,current}`. Device fields: `sn`, `name` ("Meter 1"), `status`, `preSn` (the parent inverter's serial), `isHems`, `addTime`. **No model or subtype** |

`preSn` on a meter is the inverter it hangs off, so meters could be nested under
their inverter rather than the station if that reads better.

### Station info

`gridStatus` is only present on battery/all-in-one stations
(`powerStationType: "2"`). PV-only stations (`type "1"`, `batteryCapacity 0`)
omit it entirely.

### Rate limiting

Five stations at a 60 s interval produce roughly **70 requests per minute**, and
they used to burst together at startup. Per station per refresh, about 19 calls,
of which **16 are per-device telemetry + telecounting** — the only uncached calls
in the client. Already cached: device discovery 1 h, statistics 300 s, battery
functions 6 h.

Mitigated by 100 ms request spacing (`858f1cc`) and per-account serialised first
refresh (`822bb2e`). Because each coordinator then schedules from its own finish
time, the stagger persists past startup instead of the intervals re-aligning.

### Permissions

`INVERTER_REMOTE` is necessary but **not sufficient** for control — the device
must also expose the function. All five stations report `INVERTER_REMOTE` and
`INVERTER_REMOTE_READ` under the consolidated account.

### Legacy endpoints are unavailable on SEMS+

A SEMS+ login resolves its API base to `<region>-gateway.semsportal.com`, which
answers `404 Route Not Found` for classic `/api/v3/...` and `/PowerStation/...`
routes. So every legacy fallback in the client is dead for these accounts,
including the inverter control fallback and `QueryDataloggerBystationId`.

## The open thread: device controls

**The Inverter Control switch does not work on an All-in-One, and the reason is
not what it first appeared.**

What the switch does today: writes register `80017`
(`_WEB_INVERTER_STATUS_ADDRESS`) with function id `2043643517552594945`, value
`2` = stop, `4` = `start_up`, via `setDeviceFunctionParameters`; falls back to the
legacy `/PowerStation/SaveRemoteControlInverter`.

Why it fails here:

- The client only ever queries `module: "GENERAL_FUNCTIONS"`, which returns two
  trees, `bat` and `inverter`. The `bat` tree populates correctly **when
  `batIndex` is the cabinet's `no`** (from `getEnergyStorageIntegratedCabinets`,
  e.g. `"1"`) — this is why battery controls work. The `inverter` tree is
  **empty** on this model, so there is nothing behind register `80017`.
- The legacy fallback 404s, as above.

But the capability exists. `POST /sems-remote/api/v2/address/remote/getAllDeviceFunctionTabs`
with `{"sn": …}` returns the device's real control tabs:

```
device_start_stop      quickTag=3     <- the app's Start/Stop switch
energy_management      quickTag=1
environmental_control
ac_side_settings
pv_settings
battery_set
protection_settings
general_set            quickTag=1
meter
```

`visible: 0` appears on tabs that are genuinely usable, so it does **not** mean
hidden — do not read anything into it.

### What is still missing

The per-tab **function list**, which carries the `address` and `id` that
`setDeviceFunctionParameters` needs. Everything tried returns `{}` — note `{}`
and not 404, so the routes exist and the request shape is wrong:

```
getDeviceFunctionTabMenus    module=DEVICE_START_STOP | COMMON_CONTROLS, menuCode 0-3
getTopTreeByCode             code | menuId | funcKey, v1 and v2
getDeviceFunctionParameters  menuId | funcKey
get-remote-controltype       v1 and v2
```

Sibling routes named in the decompiled app that have not been tried:

```
getAllControlTree
getAllDeviceFunctionTabsIOT
getDeviceFunctionTabMenusIOT
get-cache-device-function-parameters
/remote/get   /remote/set
```

The `IOT` variants are the strongest lead: the cabinet reports `aiType: "EMS"`,
so it may sit on an IOT control path that the classic module query cannot see.

**Fastest way to settle it:** point mitmproxy at a phone running SEMS+ and press
Start/Stop once. That yields the endpoint and body immediately, and very likely
the tab→functions call as well. Guessing parameter shapes against the live API
cost a lot of calls for nothing.

### Why this matters beyond one switch

The battery controls already work the right way: the client reads
`immediate_charge`, `stop_charging`, `end_charge_soc` and
`bat_immediate_charge_power` out of the function tree and builds a switch and two
numbers from each function's own `address` and `id`. Generalising that — enumerate
tabs, fetch each tab's functions, create entities from them — would retire the
hardcoded `_WEB_INVERTER_STATUS_ADDRESS` / `_WEB_INVERTER_STATUS_FUNCTION_ID`,
fix start/stop as a side effect, and work across models instead of only the
hardware the upstream author owns.

**Do not** hide the Inverter Control switch when the function menu looks empty.
That was considered and rejected: the hardware supports the control, so hiding it
would cement the bug rather than fix it.

## Other things to pick up

- **`is_on` on the Inverter Control switch is misleading.** It is
  `status in {1, 5}`, i.e. "producing normally", so it reads off every night and
  whenever the inverter is offline or in fault — not just when something stopped
  it. Making it honest needs to know what status a *commanded* stop reports, which
  needs hardware that can actually be stopped. Not yet observed.
- **Dongles may have more data than we think.** A field resolver in the app
  references `wirelessSignalStrength`/`rssi` and `communicationMode`/`cmmMode`,
  which sits oddly against telemetry returning `{}`. There may be another
  endpoint. The conclusion "a dongle only reports status" is only true of the
  endpoints we have tried.
- **Firmware is never captured for SEMS+ devices**, so every device shows
  `sw_version: unknown`. The device list may carry it; worth a look, and it would
  help correlate model behaviour with firmware.
- **Leftover registry entities.** `f50724e` stops creating ~40 junk entities per
  rack and dongle, but not creating an entity does not remove its registry entry.
  They linger as unavailable. Deleting and re-adding the config entry clears them.
  Automatic purging was deliberately rejected: with entities now created on
  demand, a missing value can mean a throttled request rather than an unsupported
  field, so a purge would fight the resilience work.
- **Remaining rate-limit ideas**, in order of value: raise `scan_interval` (no
  code, biggest lever with several stations); poll offline devices less often; TTL
  cache telecounting. The last one is tempting — 8 calls per refresh per station —
  but its `_web_cache` use is the midnight-rollover fix for issue #94, which users
  have relied on for years, so do not treat it as a drive-by.
- **Upstream divergence.** `f6dbf67` moves station flow off the shared `HomeKit`
  device. Upstream has an unfinished `fix/multiple-homekit` branch that instead
  keys that device by `homekit_sn`, carrying a `TODO` to replace the constant
  identifier. Their approach leaves the `GW-HOMEKIT-NO-SERIAL` collision in place
  for meter-less stations, which is exactly the bug that cost one station 23
  entities here. If upstream merges that branch, expect a conflict confined to
  that one `DeviceInfo` construction. Worth raising as an issue rather than
  carrying the difference silently.

## Working environment

- **Tests** need their own venv, because `pytest-homeassistant-custom-component`
  pins a conflicting `homeassistant`:
  ```
  uv venv .venv --python 3.14
  uv pip install --python .venv/bin/python -r requirements.test.txt
  .venv/bin/python -m pytest tests/ -q
  ```
- **Mind the HA version split.** The test harness runs 2026.9.4; the dev
  container's live instance runs 2026.8.0.dev0, and they differ. `DeviceInfo`
  gained `via_device_id` (replacing the `via_device` identifier tuple) only in
  2026.9, and `device_registry.async_get_device(identifiers=…)` is deprecated in
  2026.9 in favour of `async_get_device_by_identifier(identifier, config_entry_id)`.
  Check device-registry changes against **both** interpreters; `hacs.json` still
  claims support back to 2026.3.0.
- **Live probing** is how every fact above was established. The instance's SEMS
  credentials sit in plaintext in `config/.storage/core.config_entries`.
  `SemsApi(None, user, password)` works standalone (its `hass` argument is stored
  and unused), and
  `api._make_api_call(url_part, data=…, is_web=True, token_type="web")` reaches
  any gateway endpoint. Stick to read endpoints.
- **Three exhaustive inventory tests** in `tests/test_sensor_entities.py`
  (`test_all_entities_exist`, `test_exact_unique_ids_*`) assert the *complete*
  entity set, so any new entity fails them until their expectations are updated.
- Sending control commands to hardware is blocked by the Claude Code auto-mode
  classifier. Run such scripts yourself with a `!` prefix, or add a Bash
  permission rule.
